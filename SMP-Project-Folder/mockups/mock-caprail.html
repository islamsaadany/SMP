What the rail settles. It answers the two problems without inventing any control. Moving between projects is a click on a list that never scrolls away. And the open project is visible at all times, so carrying it from tab to tab stops being hidden state — you can see which one is selected, so it keeping its place is what you would expect rather than something you have to be told.
What it costs, plainly.
  • It is a new pattern. Nothing else in the platform has a rail — every other list is either the top navigation or an accordion. This is a third way of choosing a thing, and it will have to be explained once.
  • A capability with one project gets a rail of one, which is a column of wasted width. Below two projects the rail should probably not appear at all.
  • It does not print. Presentation mode and any export have to fall back to the projects laid out one after another, so that content exists in two arrangements.
  • Narrow screens lose it. Below about 820px it becomes a row of tabs scrolling sideways above the pane — drawn here, but it is a different thing to learn on a phone.
Two calls before I build.
  • Does the rail apply to a business unit's pillars too? The same argument holds — pillars are a list you work through one at a time. If it stays a capability-only pattern the two halves of the platform stop matching, which is the thing A13 exists to prevent.
  • Below how many projects does the rail disappear? My suggestion is two: with one project the pane simply fills the width.
