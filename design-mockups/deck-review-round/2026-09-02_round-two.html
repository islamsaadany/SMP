1–3 · Annual target, tight units, and the doubled unit healed

Pillar › Key measures

All three of your first points land on one slide, so here is the whole row rewritten.

The column becomes Annual target — which is Performance's own word since §239.2, so the projector and the page behind it stop using two names for one number.

A scaled currency reads as one token: 6M EGP, 8M EGP. The platform already holds this convention and writes it that way whenever the unit is picked — what it never did was apply it to a value that arrived with a space in it, because the rule elsewhere is never to rewrite what somebody typed. On the projector that rule costs more than it protects, so a scaled currency is normalised where it is drawn and the stored string is left exactly as it is.

And the doubled unit is healed in the same pass.

The healing is where you said — on reporting and on save — so a figure is written back clean the next time anyone touches it. That means a row nobody re-enters keeps its doubled string in the database and in the workbook, and reads clean only on screen. I think that is the right trade; if you want the stored data swept once as well, that is a migration and I would run it separately.

5 · Why the reported 2# was not read

“the actual case the reported number is already 2# I don't know why it's not reported correctly”

I put nine states through the scorer and every one of them with a figure in the outcome scores correctly. So the figure the deck can see is not in the outcome — and there is one way for that to happen that fits your row exactly.

The reporting box asks for the outcome's figure only once the outcome has a target. Before that it asks the old question — per cent delivered — and stores the answer in the old field. So a figure reported before the outcome's target was added sits in the old box for ever, and the moment the target appears the slide starts reading the outcome's benchmark (2#) beside a figure still coming from the old field (2%). Two measures, one cell, and nobody did anything wrong.

Which behaviour do you want?

A — the row says it is owed a figure. Not reported · due at 3# until somebody enters the outcome's number, which is one keystroke on the reporting page. Honest, and it means a row you thought was reported now says it is not.

B — carry the old figure across. When an outcome target is added to a tactic that already has a per-cent, treat the old number as the outcome's. Nothing has to be re-entered — but it assumes 2 meant two stores rather than two per cent, and on a row where that is wrong it invents a figure nobody reported.

C — both halves fall back. The row reads 2% / 50% — the old measure on both sides — until the outcome is reported. Nothing is ever wrong; the outcome target you set is simply ignored until it is used.

I would take A. It is the only one that never states a figure nobody entered, and the correction costs one number.

6 · No mark on the cover or the footer

“the presentation doesn't contain the logo in the cover page or the footer in any persentation”

The machinery is there and it is almost certainly empty. A unit's mark goes on large on its cover and small in the footer of every other slide — but it has to be uploaded first, at Setup › Business units › Unit marks, PNG, one per unit, SMO only. A unit with no mark shows its name instead, which is what you are seeing. On the demo the marks are baked in, which is why they appear there and not on your deployment.

Two real gaps sit behind that, and neither is something I would close without your word:

Two decisions

A supporting function can never have one. The upload lists business units only, and a function's deck never draws a footer mark at all. Merchandising, Consumer Finance and the rest will stay unmarked however many PNGs you upload. Should a function get a mark of its own, or inherit the unit it plans under?

There is no group mark to fall back on. Setup › Branding sets the tenant's colours and carries no lockup, so there is nothing for a unit without its own mark to borrow. A single Raya Trade mark, used wherever a unit has none, would put a mark on every deck from one upload.

7 · The pillars, beside each other

“suggest a design similar to what I shared where the pillars are beside each others”

Your reference concept, in the platform's own language: a row of cards, one per pillar, the name given room and nothing measured yet. No invented colour per card — the accent is the one gold rule the deck already uses, spent once across the row rather than three different hues that mean nothing.

The code is the number. RS01 is what every other surface calls that pillar, so one mark both identifies and orders it, where 01 would only order. Each pillar's own sub-line comes along where it has one.

The alternative, if you would rather read down than across

Round one drew the same content stacked, which gives a long pillar name more room and reads better at eight pillars than four cards would. Both are built from the same three facts, so the choice is only which way the eye travels.
