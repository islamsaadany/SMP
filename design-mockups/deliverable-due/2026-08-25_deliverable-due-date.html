How a deliverable and a milestone are planned, and how they are reported

Everything still open, in one page. A deliverable gets a due date back — which reverses §53.4, and reverses it on your own reason: the argument then was “it’s delivered when the project ends”, and the argument now is that some are not. It still has no owner; the project’s owner owns it.

It is reported in three states — Not started · In progress · Delivered — with In progress requiring a per-cent. I argued against a third state on the grounds that one without a number forces the score to invent one; requiring the per-cent is what answers that.

A milestone works the same way, per-cent included — Not started · In progress · Completed. Which makes the two tables one idea rather than two that happen to look alike.

The per-cent column is called %, and it types itself at both ends. Delivered reads 100%, Not started reads 0%, and only In progress opens a box — so the one number somebody enters is the one number nobody can derive. The outcome half’s last column becomes % too, computed from Actual against Target as it always was.

A due date is a quarter or a date, row by row, whichever suits the thing being planned. Q1 2026 beside 28 Feb 2026 in one table, because a workshop lands on a day and a report lands in a quarter. The same for an outcome’s measure date. The project’s Timeline stops deciding this — it still describes the project’s own start and end, and it no longer constrains the rows underneath it.

And a row is only asked for once it is due. Due means inside the open reporting cycle — the same rule outcomes have always used. Before that the row is dimmed and reads Not due, it drops out of the reported tally and out of the submit gate, and it counts toward no score. The dropdown still works, so anyone who wants to report early can.

Two things follow that neither of us asked for, and both are simplifications. With one way to report, the plan has nothing to choose, so Measured as leaves the plan pane, the workbook and the database. And the column called Reported becomes Status — at which point the milestone table, which calls the very same idea Progress, has to follow or the product carries two words for one thing on one page.

Two things to read past: dates and statuses below are illustrative, and each card is about half the width of the real pane, so cells wrap here that will not wrap in the product.

Capability › Projects — the plan pane

The deliverable half loses Measured as and gains a Due date. What a deliverable PLANS is now a name and a date — how it is measured stopped being a plan decision the moment there was one way to report it. Due date lands directly under Measure date, so the two halves agree on their last column as well as their first two. The milestone table does not change here — name, description, owner, due date is what you specified and what it already carries.

Capability › Reporting — where the figures are entered

Status is what you pick; % is what follows from it. Delivered writes 100% and Not started writes 0% — shown, not typed, because a box that can contradict the word beside it is a box that eventually will. Only In progress opens. The tally reads 5 / 8 rather than 7 / 11: the not-due deliverable and the not-due milestone are not owed this cycle, so they leave the count and the submit gate, exactly as an outcome not yet measured already does. The outcome half spans Target across two columns so the cell somebody types into, and the note beside it, stay in the same place on both halves.

The Execution figure does not move either — measured, not argued

Execution is done ÷ total today: a milestone in progress counts as nothing. Giving milestones a per-cent turns it into an average — Completed 100, Not started 0, In progress its own figure. Those are the same arithmetic when no per-cent has been entered yet, which is what every tenant looks like on the day this ships. Run across all eight capabilities in the worked example:

What this costs, stated plainly

  • Two migrations pulling opposite ways. One adds deliverables.due back after 016 dropped it; one retires deliverables.kind, which nothing will read. Any tenant that had deliverable dates before Sunday lost them from the live table, but they are recoverable from plan_archives, where every replaced plan has lived since §22.
  • The reporting pane goes to six columns for a deliverable — the widest table in the product, on the page somebody fills in under time pressure. The outcome half spans Target across two so the two halves still end on the same pair.
  • The plan template’s Deliverables sheet loses Kind and gains Due date, and the progress template gets a status and a per-cent in place of one New value column — the same pair the Milestones sheet has always had. A workbook downloaded before today still uploads: its Kind column is read and ignored.
  • One vocabulary, and one shape. A deliverable and a milestone both carry a Status and a Performance; one is Delivered where the other is Completed, which is right, because a deliverable is delivered. msStatusWord() already exists to say those words and now says them for both.
  • Overdue and not due are different things and look different. Overdue is red in the due-date cell — past its date, not finished, and being asked for. Not due is quiet — its cycle has not come, so nothing is asked and nothing is scored. The project-level overrun note is unchanged and still sits under the table.
  • One reader has to understand four shapes. A row says Q1 2026 or 28 Feb 2026; a cycle is called Q2 2026 or H1 2026. The existing test reads only quarters, so it cannot see a date at all and answers “due” for everything when the cycle is a half-year — which yours is. One reader, taught all four, used by deliverables, outcomes and milestones alike.
  • The upload check gets looser, not stricter. It was going to hold a row to its project’s Timeline; now either form is right on any row, so it says something only when what arrived is neither — which is still exactly the case that started this, Done and Pending sitting in a due-date column.
  • One field, not a picker. Behind the pen the due date stays a single box that takes either form, with the hint beside it. A quarter dropdown next to a date picker is two controls for something a person can type in six characters — and it would have to guess which one an existing value belongs in.
  • The tally changes meaning, deliberately. It becomes “what you owe this cycle” rather than “everything in the plan”. Submitting gets easier early in a project and no easier late, which is the right way round.
