These are settings somebody touches twice a year; the queue is what the page is for. §93.5 settled the same argument on the register — “this page is a table page, not for other notifications” — and §90 put the register’s own twice-a-year controls into exactly this menu.

Replying is off while the chat is off

The page has to stay reachable, and that is not a detail. If the Messages page disappeared with the chat, the only way to turn it back on would be to turn it on first. §61 hit exactly that: a supporting function with no plan could not be opened, so the only way to reach it was to give it a plan — which hid every function on a fresh tenant.

Turning it off never deletes a conversation. §44 settled this for the naming switch in one line: a switch that destroys data is not a switch. The history stays, the office can still read all of it, and turning it back on finds everything where it was.

Replying goes off with it, deliberately. If the bubble is gone, nobody can see an answer — so a live reply box would be a control that writes into the void. The alternative, letting the office reply into a chat nobody can open, is worse: the person gets an email pointing at a platform with no way to answer back.

3 · The half that is not on screen

must be built

A switch that only hides a control is decoration — this project has learned that one more than once.

THE SERVER HAS TO REFUSE, NOT JUST THE SCREEN. §42's whole argument: everything §37 built decided what a screen OFFERED; nothing decided what the server ACCEPTED. With the chat off, /api/chat must turn down say and reply outright — otherwise the feature is off for anybody using the product and on for anybody with a browser console. §44 hit the same thing and recorded it: a switch that only hides a control is decoration.

Which costs the endpoint one query it does not make today. api/chat.js has never read the strategy graph — it answers from the two chat tables and the session, which is why it is cheap. Reading five settings means one small SELECT extra FROM org, and it belongs behind the same once-per-instance guard as everything else, or the settings check undoes the saving it exists to make.

The settings ride in org.extra, so there is no migration — the same place the naming switch, the BU list and the communication settings already live. They arrive with the state graph, and the SMO's save carries them like any other setup change.

And the whole office may flip it, which was your call. Worth writing down beside the rule rather than only in the code: this one is operational, like opening and closing a cycle — whoever is staffing the desk can turn it off over a holiday without going through you.

What I need signed off before touching any source

  1. A Settings dropdown on the Messages page header, holding all five controls. Not a second Setup page, not a block above the queue.
  2. Off removes the bubble everywhere and stops all polling — and turns the office's reply box off with it.
  3. The Messages page stays in the rail while it is off, showing the history and a line saying the chat is off.
  4. Live / Relaxed for the cadence, with the cost stated in the row.
  5. Anyone in the office may change these — Super user or SMO team.
