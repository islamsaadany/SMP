Talking to the Strategy Office

A bubble in the bottom-right corner of every page opens one running conversation with the office. The office answers from a Setup page. Built, driven against a real database, and pushed to the branch — not merged.

01

You asked for this once already

“Some sort of feedback box in the bottom right of the page where the person who is using it, if he finds any issue with a page or a number, can submit an issue … and this feedback should land in the admin page.”

§71, built at v3.23

The endpoint shipped. Two tables shipped. The reply thread, the screenshot handling, the access rules and a test script all shipped — under a commit whose own message says exactly what happened: “Feedback: the server half.”

The box was never drawn. Searching the built platform for the word finds three hits, and all three are the phrase “feedback loop” in unrelated comments. Nobody could ever have pressed anything.

So this is not a second feature beside that one. It is the missing half of it, reshaped from a form into a conversation — which is the first decision below, and the one every other decision follows from.

02

The five decisions

Settled before anything was drawn, then drawn as a mockup and signed off before a single source file was touched.

The questionThe answer, and what it costs
One box, or two? One. The chat absorbs §71's feedback rather than sitting beside it. There must never be two things in the same corner.
Who is being written to? The office, not a named person — so nobody is a dead end when someone is on leave. The reply carries the answerer's name, because a reply from an institution is not a reply.
Does it leave the platform? Only when the person is away, and the office is shown which way it will go before pressing Send.
Where does the office answer? Setup › Running the cycle › Messages, second in the group, under Reporting cycle.
What is the unit of work? The person, not the ticket. One conversation each, for ever. The cost is §71's per-item statuses — see section 06.
03

What it looks like

Every image below is a screenshot of the running product — the built file served over HTTP against a local Postgres — not a drawing. The four conversations were seeded into that throwaway database so the queue has something in it; nothing invented went near the seed file or a real tenant.

The corner

It wears --panel — the colour Setup › Branding sets for the navigation bar — because it is chrome, not content, and should follow a client's brand the way the bar does.

The only accent it ever carries is that gold 1, and it counts one thing: replies you have not read. It is not a nag — if nobody has written to you, the bubble is bare. And it is not drawn at all on a projector, from a file with no server behind it, or for somebody the server has turned away.

Three things in that picture

  • The context line is the navigation's own words. The first build put “the group › performance” on a message where the screen said “Group › Performance” — it was reading a key. It reads the navigation itself now, so the two cannot drift.
  • The build id rides along (smp-shell-v3.26), taken from the service worker's cache name — the one string guaranteed to change whenever the built file's bytes do.
  • The office's replies are signed. You write to the office; a person answers.

The line above the reply box is the whole email rule

It is not decoration. The server makes the same call again when the reply lands, from the same field — a screen that predicts and a server that decides separately is exactly the drift the shared rules file exists to prevent.

04

How it actually works

Vercel serves static files and functions; there is no socket to hold open. So it polls — fast while you are looking at it, slow while you are not — and that same polling is what answers “is this person here?” when the office replies.

One conversation per person, and it is an invariant

chat_threads.person_key is the primary key. Not a rule somebody remembers to check — the database cannot hold a second one. The reason is your own sentence about it sounding like a chat: the moment somebody has to decide whether what they are typing is a new item or the same one, it has stopped being one.

Nothing in the client file ever calls paint()

This is the rule the whole thing is built around, and it is why the composer sits outside the part of the panel that gets rewritten. A full repaint would throw away the half-typed message, the focus, the scroll position and the attached screenshot — four seconds after somebody started typing. The check proves it by typing, waiting longer than the poll, confirming the poll really happened, and reading the box back.

The three things the tests found, which is the useful part

  • The outcome sentence was wiped by its own refresh. The reply said “Sent, and emailed to…” into the page, then reloaded the thread and destroyed it. The word now lives where the redraw cannot reach.
  • The office's page fetched over file://. The corner already refused there; the Setup page is drawn by the platform's own repaint and runs its own clock, so it tried anyway — a CORS failure nothing could catch. Caught by qa.py, which is why the whole sweep gets run against a change that “obviously” only touches new files.
  • The code contradicted its own comment. It said presence is stamped on a poll and not on a send — and then stamped it on a send. The test failed, the comment was right, the code was wrong.
Worth saying

Two of the first test run's failures were the check being wrong, not the product — one compared against text the page renders in uppercase, and one asserted somebody was “away” when the test's own poll a moment earlier had made them present. Both were fixed in the check rather than loosened.

06

What it cost, and the two things to decide

Your call — a destructive line

Migration 022 drops feedback and feedback_replies. My argument is that they are provably empty: no UI ever existed to write to them, so no deployment can hold a row — and two unreachable tables behind an unreachable endpoint are exactly what the next person reads as load-bearing. But migrations run automatically on the first request after a deploy, so this is the one line worth vetoing if you disagree. Say the word and they stay standing.

A real loss, recorded rather than glossed

Per-item statuses are gone. §71's new / open / done / parked stop being something the product tracks, because the unit is now the person. Flagging a message is what is left and it is deliberately weaker. If you want a proper issue tracker as well, that is a different feature and it should not ride in behind a chat bubble.

A soft edge, stated on screen rather than hidden

“Away” is decided at the moment of replying. There is no scheduler on Vercel — no cron entry — so somebody who was reading a page thirty seconds ago and then shut their laptop gets no email. That is precisely why the office is shown which way it will go before pressing Send, instead of the rule being silent. A proper sweep needs a cron entry and is a later decision.

And one rule moved house

§72 said “api/mail.js is the only place the mail key is read.” The moment a second endpoint had to send something, that had two futures: a second copy of the credential handling, or one module both call. It is lib/mailer.js now. The rule is unchanged; the address it points at moved.
