Building a plan on the platform

The SMO team picks a unit or a function — or creates one — chooses how it plans, and builds the whole plan on the platform's own pages. The builder is a map of the plan's sections, open in any order, and every row is added through a form that protects its shape.

1What is settled

The first four from the opening alignment; the two marked revised are this round's corrections and are what changed between revision 1 and this page.

✓Functions choose, units don't A unit always plans in pillars. Only a function with nothing behind it is asked pillars or projects — the existing format switch, asked at a better moment.
✓Guided mode, not a wizard The builder lives on the platform's real pages with the pen open. Reading, arranging and the score never move to a second surface.
✓Live immediately The plan appears as it is built, like pen edits today. No draft flag, no state to forget to clear; missing things read honestly as missing.
✓New or existing subject The first step offers the existing units and functions and creating a new one in place — which also gives Setup › Business units its missing "+ Add".
✓A map, not a marchrevised No forced sequence. Every section of the plan is directly openable from the band, in any order; the left-to-right order is a suggestion the band shows, never a gate. Nothing waits on a previous step.
✓A row is added wholerevised Adding an objective, measure, tactic, project, deliverable, outcome or milestone opens a form asking that row kind's fields in the outcome's order — the template protects the structure, so a row cannot arrive as a bare name with its shape missing.

6Adding a row protects its shape

Every "+ Add" in build mode opens a form — the register's §116 shape — asking that row kind's fields in the order the outcome reads them. An objective is not a name: it is a name, a direction, a target, a horizon target and a compile rule, and the form asks for all of them together so the row lands coherent with the table it joins. One form per row kind, each asking its own shape: measure — name, direction, target, compile; tactic — name, owner, quarters, collaborators; project — name, owner, start, end, brief; deliverable — name, measured as (done / % of progress), due date; outcome — name, direction, target, measure date; milestone — name, date. The name is what makes Add live; anything else left empty is named in the amber line before the row is added, and carries the page's own "missing" mark after — asked for, never forced, so "we have not set the target yet" stays sayable. Add & add another keeps the form open for building a table in one sitting.

7The review

Not a gate — an honest reading, reachable at any moment from Finish building or its own chip. Empty is allowed (a unit may genuinely have no SWOT yet); the review names every gap so finishing with one is a decision, not an oversight. Each row jumps to its section.

8What this costs, and what it touches

An audit of every empty state comes first

The editors were built for correcting an imported plan, so some first-rows cannot be written — an empty unit's "Who we are" has no way to add its first clause. Part one of the build is walking every authoring surface from a truly empty subject and fixing what cannot start from nothing. The builder is only as good as these.

The row forms are the register's dialog, generalised

§116 already moved the register's editing into a dialog because a form crammed into table cells collides with everything around it. The builder's row forms are the same shape: one dialog component, one field list per row kind, declared once — and the field lists are the same vocabulary the plan's tables and the import template already use, never a second copy.

Setup › Business units gains "+ Add a unit"

Name, code prefix, company, weight — the same shape functions already have. The builder's "+ New business unit" and this button are one function, never two. A new unit starts unweighted and the weighting page says so.

Almost nothing new on the server

Every edit the builder makes is a plan edit the server already classifies (unitPlan / capPlan); creating a unit or function is setup, which is already the SMO's. No new stored state — the band's chips are derived from the plan itself.

Deliberately not in this module

Units planning in projects (settled: functions only). Draft visibility (settled: live immediately). Templates or pre-filled example plans. Changing anything about how the xlsx import works — the two doors stay siblings.
