What this page is

  • One list, again. Every row here is a row of the plan — the same array, the same figures. The count at the top of the Plan page and the count at the top of this one cannot disagree, because neither is typed.
  • Done is not Completed, and this is where the second step happens. Whoever did the work marked it done; a Lead accepts it and sets the real end date. Until then it sits here. That is a governance rule, not a status list.
  • The page says what is true; the controls are drawn for whoever holds them. Press the three names above. A Contributor reads the same four sections and is offered no sign-off; a Viewer is offered nothing at all. Nothing is hidden from anybody — what changes is what can be pressed.
  • A gold edge means this one is yours to do. Look as Omar: 2.3 is his and it is eleven days past its date. It is drawn on what is owed and never on what is finished — marking a Lead's own signed-off rows would be a colour that means nothing.
  • An empty section says so and does not nag. A project with nothing waiting is a healthy project, not a screen that failed to load.

The real end date, and why it is bounded

  • It is never typed on the way in and never invented. The real start is stamped the first time progress leaves nought; the real end is stamped here, on sign-off, and cleared if the activity is reopened.
  • Not before the day the work was marked done — 2.2 was marked done on 24 February, so no earlier date is accepted.
  • And if the work was on time, not after the planned end either. That rule is the one nobody expects, so the row says it rather than letting the server refuse a date somebody has already chosen. 2.2 ran four days over, so its upper bound is open; an activity finished inside its window cannot be signed off into next month.
  • The bound is shown by the screen and enforced by the server, which is the same rule twice on purpose — a screen that only narrows a picker has narrowed nothing.
  • Reopening is gated exactly like signing off. Their version needs only the work-on permission, so a Contributor can undo a Lead's sign-off and clear its date. Here it is the Lead's, or the two-step rule is a formality.

What is owed, and why these three

  • Past their date is the count the Plan page carries too. Red on the date itself, with how far past.
  • Nobody is on these is the section the spec asked for before this page existed: unassigned activities in a live plan are what nobody notices until a checkpoint. Three of this project's activities have no name against them, all of them in the phase that has barely started.
  • Signed off is here so the page is not only a list of problems, and so that undoing one has somewhere to be done from.
  • Blocked is deliberately not a section. 2.3 cannot start because 2.2 has not finished — which is a fact about 2.2, already counted above, and listing it twice would make one activity read as two things owed.

Two things this drawing does not decide

  • The checkpoint is a line, not a mechanism. The spec says checkpoints are weekly or monthly and per project, and says nothing else — so the strip names the next one and this page invents no cadence, no record and no state around it. What a checkpoint actually does, if anything beyond a date, is a decision.
  • Analytics has no drawing and cannot honestly have one yet. The audit names its files and never says what it renders — 985 lines of page plus a builder for grouping phases into coloured buckets — so anything drawn for it now would be invented rather than ported. It needs either sight of the reference or a decision about what a client is meant to read there.
