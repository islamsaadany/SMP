Deliverable or Outcome

Two things you hit while creating a project, drawn in the running platform on Finance › Strategy › Projects with the pen open. Nothing is built yet.

“on a creation of a project I couldn’t set the direction and we need to make the add deliverable or outcome more of an options in the type rather than 2 buttons of add deliverable or outcome that I get confused between them”
1

What is actually wrong

They are two different kinds of fault. The direction is a straight omission. The two buttons are a design decision that has stopped working.

The direction
It has never been editable, on any project, in any mode. The cell prints the sign as plain text and stops there. A deliverable’s = is right to leave alone — it is written for the row, not asked of it — but an outcome’s ≥ / ≤ should open with the pen, exactly as a pillar’s key measure has since we opened those.
The two buttons
They render with no space between them. Measured on the live page and visible in your own screenshot: the row reads Add a deliverableAdd an outcome as one run of underlined text. So part of the confusion is that they do not even look like two controls.
And a third
A row added as the wrong kind cannot be corrected. There is no way back except removing it and adding it again.
2

What “type” is, before we make it a picker

Worth saying plainly, because it decides how far the picker can go. The type is not a label on the row — it is which of two lists the row is in, and the two are reported and scored differently:

A deliverable is answered Not started / In progress / Delivered, with a per-cent while it is in progress. It has no direction and no target of its own; the = and the Y/N are printed for it.
An outcome is answered with a figure, read against a target and a direction.

So changing a row’s type is a real conversion: the row moves between the two lists, takes a new code, and loses whatever the other kind cannot hold. If a figure has already been reported against that row, that figure goes with it. That is the only thing in this whole change worth being careful about.

Nothing on the server has to change. A row leaving one list and appearing in the other is already classified as a plan change, which is the office’s.

3

Three ways to draw it

Each shot is the real pane with the real pen open, at 1600px. The direction picker is in all three — that part is not in question.

Today

Two buttons, nothing editable but the name and the target

Type and Direction are plain text on every row. The add row is the run-together pair.

A

The type is a picker on every row, and one way in

One + Add a row. The kind is answered in the column that already names it, and a row added wrong is corrected in place. Cost: the type column takes 16px from the name column at 1600 (433 → 417), and a row that has been reported against can lose its figure without being asked.

B

The kind is answered once, at the moment of adding

The Type column stays as it is; the add row becomes one control. It costs no width and nothing can be destroyed — and it does not fix a row already added as the wrong kind.

C — recommended

A, and the type stops being a picker once something has been reported

Row 1 has a figure against it, so its type is drawn as text with the reason on the hover — a figure has been reported against this row this cycle, so its type cannot change. Every other row is a picker. The width is identical to A, because the reason is on a hover rather than on the page.

What I would build, and why

C, in one pass with the direction fix.

  • The Type column becomes the picker, which is what you asked for and puts the answer in the column whose heading already asks the question.
  • One + Add a row, so there is nothing to choose between before you have typed anything.
  • An outcome’s direction opens with the pen; a deliverable’s = stays printed. The direction stays the office’s and is not a missing item, so no count and no Submit gate moves.
  • Once a figure has been reported against a row, its type is drawn as text with the reason on the hover. Nobody loses a reported number by changing a dropdown.

The alternative to the lock, if you would rather never be blocked: leave the picker live always and ask for confirmation when a switch would throw a reported figure away. It is more to build and it puts a dialog in front of an edit.

Say the word and I build it — or tell me A, B, or C with the confirmation instead. Nothing has been changed in the sources yet.
