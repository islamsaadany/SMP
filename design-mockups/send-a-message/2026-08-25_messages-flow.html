Messages — how the page should work

Islam: “when I open Send a message what I see is the drafts and what has been sent — maybe a button to create a new message that opens the whole message creation thing.” Right, and it changes what the page IS: a list of messages, with composing as something you start from it.

The flow

1Messages Drafts and sent in one list, newest first. This is what opening the page shows.
2+ New message Creates the draft and opens it. There is no unsaved state to lose.
3The draft Who · write · preview · send. Its own screen, reachable again from the list.
4Confirm Names the number — and the server refuses if it has changed since.
5The record A sent message is not an editor. It shows who got it, at which address, and what failed.

Taken from HR_ERP's Communications, which already solved this. The two ideas worth copying outright are that New message creates the draft immediately and navigates into it — so nothing is ever half-written and unsaved — and that a sent message is a RECORD rather than a locked editor.

SMP already stores everything that record needs and shows none of it. message_recipients holds the person, the address it went to, whether it was accepted and the provider’s error; messages.audience holds the criteria as they were ticked. Today the page shows “45 of 47” and nothing else, so “which two, and why” is unanswerable from the screen.

One list, not two. A draft and a sent message are the same thing at two stages, and Status is what says which — the register's own lesson, applied (§93.14). It means “what happened to the Q3 one” is one search rather than a decision about which table to look in. The row menu offers what that row can do: a draft gets Open and Delete; a sent one gets Read it, See who got it and Duplicate.

“2 failed” is a status, not a footnote. Today a failure is a number in a column you have to go looking for; here it wears the same amber the register uses for something that needs a person.

“Accepted” means the mail provider took it. What happens after that — a full mailbox, a spam folder — is outside what this platform can know.

Every column here is already in the database and has never been on a screen. “45 of 47” tells you two people missed it; this tells you which two, at which address, and why — which is the difference between a number and something you can act on. It is the same argument as naming the skipped people rather than counting them (§87).

And the confirmation binds the number

a correctness fix, not a design one

HR_ERP's rule, worth copying word for word: “the send is behind a dialog that NAMES the number of people — and that number is passed to the server, which refuses if it has changed since. A confirmation that can silently cover more people than it named is not a confirmation.”

SMP does not do this today. The browser's confirm() names a count the page worked out, then the server re-resolves the audience from the stored register and sends to whatever it finds. Add somebody to a unit in another tab between reading the number and pressing Yes, and the message goes to more people than the confirmation named — silently, and it cannot be recalled. The count travels with the send and the server refuses a mismatch.

The changes, in order of what they are worth

  • The page opens on the list. Two of the three jobs were buried under the third.
  • New message creates the draft and opens it — nothing is ever unsaved.
  • A sent message opens as a record, with the per-person delivery table SMP already stores.
  • The confirmation binds the count, and the server refuses if it moved.
  • One list with a Status column, not two sections — the register's own lesson.
  • The audience becomes two counts and a disclosure, so Send holds still.
  • The button folds into the message.
  • Duplicate a sent message — the quarterly reminder is the same message with two words changed.
  • Send me a copy first.

Not copied from HR_ERP, deliberately: its Communications page is a door to three things — noticeboard, email, congratulations. SMP has one of those, so a chooser in front of a single destination is a door behind a door (§32). And its “preview as a business unit” exists because HR_ERP brands each copy by the recipient’s unit; SMP brands per tenant, so there is one thing to preview and it is already on screen.
