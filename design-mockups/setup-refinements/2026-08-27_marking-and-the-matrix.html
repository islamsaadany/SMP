Item 6

Focus measures

Four changes in one screen: the note goes, the chips go, the big button becomes a switch on the pinned line, the dropdown becomes a row of destinations, and the list becomes a table headed the way the register is.

  • On / Off, on the pinned line. The platform's own segmented control — the same one Units | Functions wears in the navigation — so it is a switch and reads as one. The page title already says what is being switched, so it carries no label.
  • The destinations, the way the navigation does them. Units | Functions and then the places themselves, with each one's mark count on it. The dropdown hid where the work was left; this puts it on the row — Mobile 3, Retail Stores 2, Care 2, Logistics 2, and the rest bare.
  • One table. Navy uppercase head, hairline columns, banded by key objectives and then by pillar — the register's own furniture. Measure, Target, Focus, with the mark last, because that is the column you run your eye down.
  • The grey note and the three chips — gone, and with them a bug that was printing “0 0 marks” whenever the switch was off.
This one needs your answer before I build it

Seven of the eight supporting functions have nothing a measure could be marked on. Only Merchandising plans in pillars, so only Merchandising has key objectives and pillar measures the way a unit does — for it, the Functions side works exactly as the Units side does and costs almost nothing. The other seven plan in capabilities, and their measurable rows sit one level down, inside each capability.

So: for a capability function, should its capabilities' key objectives be what you mark? That is the closest thing to a unit's list and my recommendation — banded by capability instead of by pillar, so the table looks identical.

And one consequence to accept with it: the Focus board on the group page reads units only. If functions can be marked, that board needs a functions half in the same change, or the marks are stored where nobody can see them.

Item 10

Roles & access

You were right that the design was damaged. It has one cause, and it is the fault the section that introduced sticky table heads wrote down about a different table.

What was actually happening

This table sits in a horizontally scrollable box, which makes that box — not the page — the thing its header pins against. The header was then given the page's offset of 141px, so instead of sticking to the top of the window it was pushed 141px down inside the table, landing on rows three and four. Measured: every one of the twelve header cells reports the same position.

Two tables were already excluded from that rule for exactly this reason — the register and the who-enters table. This one was missed. It joins them, and because the whole matrix scrolls only 60px on a normal window, its head simply sits at the top of the table where it belongs.

And it was hiding something. With the header repaired you can read what the columns have been saying all along: Own business unit and Own supporting function each split into Strategy and Reporting. Those two group headings were the part being covered up.

  • The briefing paragraph goes, as on every other Setup page — which also cuts the page's scroll from 137px to 60px at 1280×720.
  • Nothing else about the matrix changes: same roles, same columns, same cells.
