The measurement

Why quality was never the question

You asked whether to squeeze on the way in or squeeze after the cycle. Both keep the clip in the state graph, and that is the part that does not work. Here is what a clip would sit beside.

WhatSizeWho downloads it, and when
The whole tenant’s data today297 KB Everyone, on every sign-in
One picture slide, as stored now150–300 KB Everyone, on every sign-in
A 2-minute clip at 720p20–40 MB ≈ 100× the entire platform, per clip
…squeezed hard, to 480p and 30 seconds≈ 2 MB Still 7× everything else in the tenant

Pictures ride inside that 297KB — review.extra, one JSONB column in one row — and GET /api/state returns all of it to every person on every page load. Compression moves the number. It does not move the order of magnitude.

Ruled out Squeeze after the cycle. It makes the busiest week the heaviest one — everybody uploads full-size in the days before the review — and Vercel gives us no scheduler to run the squeeze on (§97.5 already records that). It also re-encodes stored evidence after the fact, which cuts against §49.2: a record somebody tidied is no longer the record.
Blocked Storing the clip at all, at any quality. Vercel refuses a request body over 4.5MB, so a save carrying a clip fails outright — at a reporting deadline. And today’s CSP sets no media-src, so it falls through to default-src 'self' and a data: video will not play; frame-src 'none' blocks an embed. Neither route works without a deliberate change.
The shape

The graph holds a pointer; the bytes live outside it

A slide stores a few hundred bytes — where the clip is, how long it runs, how big it is — plus a poster frame grabbed in the browser exactly the way a picture is shrunk today. The clip itself goes to a Vercel Blob store: the same account, one setting in the dashboard, no new vendor.

On upload Straight past us

Our function checks the session and mints a signed upload address. The browser sends the file directly to the store, so 50MB never passes through a serverless function and the 4.5MB cap is never touched.

In the plan A pointer and a frame

The slide keeps the address, the length, the size and a poster image. Everything a deck needs to draw the slide correctly — including when the clip cannot be reached.

On the projector A signed address, expiring

Opening the deck mints a short-lived address for that viewer. Only somebody signed in who may see that deck gets a playable link, and it stops working afterwards.

Answers 03 And it is what makes clearing possible. Once the bytes are their own objects they can be counted, listed and deleted one at a time — which is exactly what a clip buried in a JSONB column could never be.

What it costs

Three things this spends

The page’s security policy has to be widened

The issue
The platform allows connections and media from itself only. A clip on a storage host, or an embed, is refused by the browser today.
How it hurts
Every host we allow is a host an injected script could also reach. The platform still runs inline script, so this is a real widening, not a formality.
The fix
Name the storage host and the two embed hosts explicitly — never a blanket https: — and let the office add its own host on the Video storage page, so any further widening is the tenant’s own deliberate act.
The cost
Three named hosts in vercel.json, and a new check that proves an injected handler still cannot run.

A blob store has to be turned on, by you

The issue
The bytes need somewhere to live that is not Postgres.
The fix
Vercel Blob, in the same project as the deployment — created in the dashboard the way the Neon database was. Private storage, which went generally available in June, so a clip is reachable only through a signed address we mint for a signed-in viewer, never a public URL.
The cost
One dashboard step I cannot do for you, one dependency (@vercel/blob), and roughly $0.02 per GB a month plus a few pence per GB watched. At a full cycle across every unit that is cents, not dollars — the money was never the problem; the database was.

A deleted clip leaves a slide behind

The issue
Clearing storage frees bytes that an archived review still points at.
The fix
The archived slide keeps its poster and caption and says the clip was removed, and when. It is never drawn as a dead player — an absence is stated, not rendered as something that failed to load (§15.1).
The cost
A past review can no longer be played back in full. That is the trade you accepted by choosing “keep, with a way to clear”, and it is worth restating rather than discovering.
Before I build

Four things left to say

  • Sign off the screens above

    Rule 1c — nothing in the sources gets touched until you have looked at these. If any of the four is wrong, it is cheaper to redraw it now.

  • Which link hosts?

    YouTube and Vimeo are one line each. SharePoint and Google Drive are the ones a corporate client actually uses, and each is another named host in the policy.

    My recommendation: YouTube, Vimeo and SharePoint built in, the rest added by the office.
  • How many clips per subject, per cycle?

    Pictures are capped at 12 slides. A video cap decides the worst case a cycle can cost.

    My recommendation: 3, sharing the same 12-slide limit.
  • Who may add one?

    A picture slide is authorised as speaking for the unit — custodian, owner, and the office. A clip is the same act in front of the same board.

    My recommendation: the same rule, unchanged. No new permission.
