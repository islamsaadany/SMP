Decision 1 — the navigation below ~1100px item 01 · §118.7

The root cause turned out to be one contradiction: the row is told to wrap (arrange.css) and told to stay 46px tall (_shared.css) at the same time — so it wraps, the box never grows, and the second line paints outside it, over the tab row.

Today BROKEN

Candidate A — the row wraps, and the chrome owns its height RECOMMENDED

The 46px becomes a minimum instead of a law. The row takes a second navy line when it needs one, and the chrome’s existing ResizeObserver (it already publishes --chrome-h) tells every sticky element about the new height — nothing else has to be taught anything.

tab receives its click — measured --chrome-h 168 → 220px at 1024 at 1440: unchanged (row fits, one line)

Why A: everything stays on screen, always — nothing to discover, nothing to scroll. The cost is honest and only paid where today is broken: about 52px of page height at narrow widths.

Candidate B — one line that scrolls sideways NOT RECOMMENDED

The row keeps one line and scrolls, with a fade at the edge saying it continues. It costs no height — and the live test showed its real price without being asked:

A destination you cannot see is a destination that does not exist for a first-time viewer, and the control that switches Units and Functions must never leave the screen. B is the right pattern for a long list of equals; this row also carries controls, and they are what scrolls away.

Decision 2 — the failure card item 03 · §118.7

Today a page that dies mid-render leaves the previous page on screen and says nothing. On a throw, the panel will say so instead — in the platform’s own tokens, both themes:

What it says, and why: the failed page is named; the first sentence answers the fear (“nothing you saved is lost, the navigation still works”); the error itself is shown in one quiet mono line; and there is one action — Reload. An earlier draft had a second button, “Open another page” — it went, because the navigation is right above and a control that does nothing concrete is worse than no control.

One open point for you: the mono line ends “kept for the Strategy Office”. That clause ships only if we also write the error to the change log so the office can actually see it later — a small, worthwhile addition, but it is storage, so it is your call. If not, the clause is dropped and the error is on-screen only.

Item 02 — the autosave flush §126.1

No visual side, so nothing to sign off here — stated for completeness: the pending save flushes when the page is hidden or closed (visibilitychange / pagehide), in sync.js — one place, because there is one autosave. Nothing changes on screen; what changes is that the screen stops being ahead of the database.

Proof before handover: the round trip against a real Postgres, plus a new check that edits a setting, leaves the page 150ms later, and asks the server what it holds — watched to fail on the current build first.

What I need from you: a yes/no on Candidate A (or B, or neither), and a yes/no on the failure card — including whether the error is also written to the change log. Nothing is built until then.
